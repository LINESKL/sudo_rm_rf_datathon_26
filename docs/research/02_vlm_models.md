# 02. Открытые VLM для верификации кандидатов-событий (CCTV, кассовая зона)

Дата ресёрча: 2026-10-17. Ограничения задачи: полностью локально, лицензия весов допускает коммерческое использование, < 5 минут на видео (10-145 с, 464x848, 30 fps), устойчивость к незнакомому ракурсу и незнакомым типам нарушений.

Как читать пометки:
- **[П]** проверено по первоисточнику (карточка модели на HF / HF API / LICENSE-файл / статья), URL в разделе "Источники".
- **[О]** моя оценка расчётом (FLOPs, пропускная способность памяти). Не замеры. Перед выбором железа сделать 15-минутный бенчмарк (раздел 9).
- **[?]** не удалось проверить; не опираться без проверки.

Главное: ландшафт к октябрю 2026 сильно сдвинулся относительно Qwen2.5-VL/InternVL3. Актуальные сильные семейства: **Qwen3.5 / 3.6 / 3.8 (Apache-2.0, нативно мультимодальные, видео из коробки)**, **Gemma 4 (теперь Apache-2.0, не "Gemma Terms")**, **MiniCPM-V 4.6 / 4.7 (Apache-2.0, вышла 6-7 октября, почти не обкатана)**, Qwen3-VL (Apache-2.0, самая обкатанная в serving).

Заметки:
1. **Qwen3.5/3.6 - гибридная архитектура** (Gated DeltaNet + Gated Attention, 3:1) [П]. KV-кэш маленький, длинный контекст дешёвый, но софт-стек свежий: нужны новые vLLM/SGLang; на 24 ГБ под vLLM возможны ошибки размера Mamba-кэша (в рецепте совет уменьшить `--max-cudagraph-capture-size`) [П]. За 24 часа это риск: **держать Qwen3-VL-8B-Instruct как "зелёный" запасной вариант** (зрелый стек).
2. **Qwen3.5 по умолчанию в режиме thinking** (`<think>...`) [П]. Для верификации включить `chat_template_kwargs={"enable_thinking": false}` (или `--default-chat-template-kwargs '{"enable_thinking": false}'` в vLLM) - иначе десятки секунд лишних токенов на окно и поломка короткого JSON.
3. **llama.cpp не получает видео напрямую**: подавать окно как N изображений (это и так наш план).
4. Структурированный вывод в vLLM: `extra_body={"structured_outputs": {"json": schema}}` (xgrammar/guidance); старые `guided_json` и др. удалены в v0.12.0 [П]. С парсером рассуждений и Qwen-моделями возможны нюансы (`enable_in_reasoning`) - отключение thinking снимает проблему. Для мультимодальных моделей страница документации не гарантирует поведение [П: не покрыто], проверить на месте.
5. Заявленной пропускной способности (tok/s) для Qwen3.5 на 4090 с vLLM в первоисточниках **нет** [П]. Сторонние сайты дают ~90-126 ток/с декода Q4 на 4090 для 9B (оценочные страницы willitrunai, не замеры) [?].

## 6. Рекомендации top-3 по железу

Допущения для оценок [О]: окно = 6 кадров с кропом/ресайзом ~336x600 (Qwen: токен на 32x32 px -> ~190-200 токенов/кадр), промпт ~400 токенов, JSON-ответ ~100 токенов, thinking выключен. ~1.6-1.8K входных токенов на окно. Видео в окне подаётся как 6 изображений (надёжнее, чем нативное видео, см. раздел 7). Время = префилл + энкодер + декод; "пакетом" = vLLM с 4-8 параллельными запросами. Сканирование всего видео (145 с, 2 fps, 320x576, временное слияние x2 => ~26K токенов) - отдельная строка.

### 6.1 Одна арендованная GPU (RTX 4090 24 ГБ / L40S 48 ГБ / A100 40-80 ГБ)

| # | Модель | Как запускать | VRAM | ~40 окон последовательно | ~40 окон пакетом | Скан всего видео |

## 7. Как подавать видео и получать точный таймкод

### Мульти-изображение vs нативное видео

| | Мульти-изображение (N кадров) | Нативное видео (`video` / `video_url`) |
|---|---|---|
| Контроль | Полный: выбираем кадры, кропы, разрешение, подписи времени | Определяет процессор: fps, `total_pixels`, ограничение токенов |
| Время | Нет встроенного, добавляем текстом | Qwen3-VL/3.5: тексты вида `<3.0 seconds>` перед каждым временным патчем [П]; слияние 2 соседних кадров в патч |
| Токены | Больше (кадр = целое изображение) | Меньше (временное слияние x2) |
| Поддержка | Везде (vLLM, SGLang, llama.cpp, MLX, Ollama) | vLLM/SGLang/Transformers; llama.cpp нет |
| Для нас | **Основной режим верификации окон** | **Режим сканирования всего видео** |

Рекомендации:
1. Верификация окна: 4-8 кадров (равномерно + кадр момента + 1-2 кадра "до"), каждому кадру добавить **подпись `t=12.4s`** текстом в промпте и/или впечатать в левый верхний угол. Параллельно подать **кроп ROI** (человек/рука/предмет) в бОльшем разрешении.
2. Сканирование (поиск неизвестных нарушений): нативное видео, 1-2 fps, ресайз ~320x576, thinking выключен, промпт "перечисли события и интервалы в формате JSON". Qwen по умолчанию 2 fps, лимит токенов на видео 256-16384 [П]; для длинных видео в Qwen3.5 нужно поднять `size` в `video_preprocessor_config.json` (карточка предупреждает, что по умолчанию консервативно) [П].
3. Видео в портретной ориентации: проверить, что ffmpeg применяет поворот из метаданных .mov (displaymatrix); иначе модель увидит боком.

### Frame-accurate таймкоды

1. **Источник истины - не VLM.** Таймкод события = PTS кадра из ffprobe/PyAV (`frame.pts * time_base`), а не `idx/fps` (.mov может быть VFR). Окно кандидата фиксирует детектор/трекер.
2. VLM используем для (а) подтверждения класса в окне, (б) грубой привязки "в каком из кадров 1..N событие началось". Просить в JSON **номер кадра/подпись `t=`**, а не свободное время.
3. Уточнение границ: на подтверждённом окне прогнать **покадровый yes/no** (по 1-2 кадра + подписи) по сетке 0.5-1 с и взять первый/последний "да" -> бинарный поиск границ. Дёшево (10-20 коротких запросов, префикс кэшируется).
4. Для событий из скана всего видео: VLM даёт интервал с погрешностью секунд (Qwen3-VL-8B ~48 mIoU на Charades-TimeLens [П]); всегда перепроверять узким окном вокруг интервала +-3 с по п.3, не публиковать таймкод напрямую.
5. Каждое нарушение сохранять с N опорными кадрами (кадр старта, пик, конец) - это evidence frames; в имени файла - PTS.

## 8. Промптинг для бинарной верификации с минимальными галлюцинациями

1. **Один вопрос - одна проверка.** Вместо "есть ли нарушение?" - чек-лист из строго наблюдаемых признаков, каждый yes/no/unclear: "рука держит телефон", "экран телефона обращён к лицу", "предмет на столе - личная сумка" и т.д. Итог собирается кодом по правилам (например, `phone_in_hand AND looking_at_phone`), а не мнением модели.
2. **Разрешить "unclear"/"not_visible"** и явно сказать: "если не видно, отвечай unclear". Известный перекос VLM к ответу "yes" (POPE) гасится: нейтральная формулировка, балансировка негативных вопросов, отсутствие намёка на ожидаемый ответ в вопросе.
3. **Структурированный вывод + guided decoding.** JSON-схема с enum; порядок полей: сначала `observations` (что видно, коротко, до 25 слов), затем `checklist`, затем `verdict`, затем `confidence`. vLLM: `structured_outputs.json`; llama.cpp: GBNF/`json_schema`; Ollama: `format` со схемой; MLX: Outlines/xgrammar-совместимые обёртки [?]. Thinking выключен, `temperature=0` (или 0.7/top_p 0.8 по рекомендации Qwen для instruct-режима, если вывод зацикливается).
4. **Калибруем уверенность по логитам, а не по словам.** Для критичных чек-пунктов брать вероятность токена `yes`/`no` (logprobs) и порог подбирать на валидации. Так получаем score, пригодный для компромисса precision/recall.
5. **Self-consistency там, где важно.** 3 прохода: разные подвыборки кадров и/или порядок/кроп, голосование большинством; расхождение => статус `uncertain` и отправка в более сильную модель (35B-A3B) или в ручную очередь. Стоимость x3 только для окон, где первый проход положителен.
6. **Два масштаба.** Сначала общий кадр, затем кроп ROI; нарушение подтверждается, только если ROI-проход согласен с общим.
7. **Контрольные негативы.** Для каждого класса держать 5-10 "почти похожих" негативных окон (человек почесал лицо vs телефон у уха) и гонять на них регрессию при смене промпта.
8. **Для неизвестных типов нарушений**: отдельный открытый промпт скана (JSON со списком `events[{start,end,what,why_violation,evidence}]`) и поверх - второй проход "подтверди каждое событие, цитируя видимые признаки". Выдавать как категорию `other` с пониженным приоритетом.
9. **Язык.** Классификацию и чек-лист - на английском; описание на русском в отдельном поле (см. раздел 5).

## 9. План на ближайшие часы (24 часа до дедлайна)

1. Первые 30 минут: поднять **Qwen3-VL-8B-Instruct** в vLLM (зрелый стек) и прогнать на 3 реальных клипах - это гарантированный базовый вариант.
2. Параллельно попробовать `Qwen/Qwen3.5-9B` (vLLM>=0.17, thinking off). Если стек стабилен - сделать его основным.
3. Бенчмарк на выбранном железе: 20 окон x 6 кадров, замерить p50/p95 времени и пик VRAM; пересчитать таблицы раздела 6 (они расчётные).
4. Не тратить время на InternVL, Molmo2, LLaVA, Phi - они не лучше по качеству/риску.
5. Если на выбранном железе окно укладывается хуже 4 минут на 145-секундное видео, сократить число окон (приоритет по скору детектора), а не качество кадров.
