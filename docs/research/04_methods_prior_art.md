Дата: 2026-10-17. Контекст: 42 обучающих ролика (22 нарушения с одним таймкодом без типа, 20 чистых), тест 5+ роликов, последний с другого ракурса и возможными новыми типами. Нужны только локальные открытые модели, лица не распознавать.
Связанный файл: `../violation_hypotheses.md` (гипотезы по типам).

## 1. Главный вывод (читать, если мало времени)

1. Обучать с нуля или дообучать видеомодель на 42 роликах бессмысленно. Побеждает **обучение-free конвейер**: детерминированный «детектор событий» (кассир ушёл, вошёл посторонний, сумка на столе) + **набор узких бинарных вопросов к VLM по кропам/кадрам** в моменты событий + **калибровка порогов на 42 роликах**.
2. Ближайшие по духу работы: **VERA** (узкие «guiding questions» вместо общего «найди аномалию»), **AnomalyRuler** (правила, выведенные из нормальных примеров, затем дедукция по правилам), **LAVAD** (подписи к кадрам, затем LLM-оценка по тексту). Наш чек-лист из `violation_hypotheses.md` — это и есть rule set в смысле AnomalyRuler/VERA, только составленный человеком.
3. Нарушения «о деталях состояния» (ноутбук разблокирован, ключ в сейфе, телефон в руке) хорошо решаются **вопросами по увеличенному кропу в нужный момент**, а не просмотром всего ролика целиком. Общие видео-LLM плохо видят мелочи при низком разрешении (464×848).
4. Для **новых ракурса и типов** лучший прокси-тест у нас уже есть в данных: минимум три ракурса камеры. Делать **leave-one-angle-out** вместо случайного CV. Плюс записать свои ролики (разрешено).
5. Политика решения: вердикт «нарушение» при низком пороге **плюс** вторая стадия проверки, которая режет ложные срабатывания; при неуверенности по ролику отдавать «нарушение» с пометкой `needs_review`, но без выдуманного типа (подробно в п. 5).

## 2. Prior art

### 2.1 Zero-shot / training-free аномалии в видео с VLM/LLM

| Работа | Идея | Что взять | Ссылки, лицензия |
|---|---|---|---|
| **LAVAD** (Zanella и др., CVPR 2024) | Покадровые подписи VLM, LLM чистит/агрегирует их по времени и ставит оценку аномальности; без обучения | Схема «кадр → текст → LLM-рассуждение по правилам». Для нас: подписи делать **целевыми** (что на столе, что на экране), а не общими | [arXiv 2404.01014](https://arxiv.org/abs/2404.01014), [проект](https://lucazanella.github.io/lavad/). Лицензию кода проверить |
| **AnomalyRuler** (Yang и др., ECCV 2024) | Две стадии: индукция правил из нескольких нормальных примеров, дедукция правил на тесте; сглаживание восприятия, агрегация правил, устойчивое рассуждение | Прямой шаблон: у нас 20 чистых роликов → «что норма»; правила нарушений → список вопросов. Сглаживание по соседним кадрам против шумных ответов VLM | [arXiv 2407.10299](https://arxiv.org/abs/2407.10299), репозиторий Yuchen413/AnomalyRuler на GitHub (по выдаче). Лицензию проверить |
| **VERA** (Ye и др., CVPR 2025) | Замороженный VLM, «guiding questions» оптимизируются вербально парой learner/optimizer VLM на грубо размеченных видео; вопросы дают сегментные оценки, затем уточняются до покадровых | Идея **оптимизировать формулировки вопросов по метке «нарушение/нет»**. У нас 42 ролика — можно вручную/полуавтоматически итерировать вопросы по LOO-метрике. В статье пример с InternVL2-8B | [arXiv 2412.01095](https://arxiv.org/abs/2412.01095). Код/лицензию проверить |
| **Holmes-VAD** (Zhang и др., 2024) | Временной сэмплер выбирает кадры с высоким откликом, MLLM дообучен (LoRA) на VAD-Instruct50k для объяснений | Принцип «сначала дешёвый отбор кадров, потом дорогое объяснение». Дообучение нам недоступно по данным и времени; веса и датасет по анонсу «будут выложены», наличие не подтверждено | [arXiv 2406.12235](https://arxiv.org/abs/2406.12235), [страница](https://holmesvad.github.io). Лицензию проверить |
| **VideoAgent** (Wang и др., ECCV 2024) | LLM как агент итеративно запрашивает у VLM новые кадры, пока не хватит информации; по выдаче 8.4 кадра в среднем на EgoSchema | Стратегия выбора кадров: **не кормить весь ролик**, а запрашивать кадры вокруг гипотез. У нас заменяется детектором событий (быстрее и воспроизводимее) | [arXiv 2403.10517](https://arxiv.org/abs/2403.10517). Не путать с одноимённым VideoAgent (Fan и др.) с памятью объектов |
| **Бенчмарки VLM по абсолютной временной локализации** | Выдача указывает: большинство VLM, включая Qwen2.5-VL, достигают меньше половины человеческого уровня в абсолютной временной локализации | **Не доверять VLM таймкод.** Таймкод брать из своего трекера/детектора событий, VLM использовать только для ответа «да/нет» на кадрах | [Know-Show, arXiv 2512.05513](https://arxiv.org/abs/2512.05513) (вторичная оценка) |

Что **не** брать: готовые VAD-датасеты и модели UCF-Crime/XD-Violence ориентированы на драки, ограбления, взрывы. Наша задача про регламент, а не про «яркую» аномалию; полезны только как метод.

### 2.2 Процедурный/регламентный контроль по видео

- **Sweethearting / кассовое мошенничество в рознице.** Классика: Bobbitt, Connell и др. (IBM, оценка на реальном магазине): кандидаты-события по движению на кассе, фильтрация ложных тревог по пространственно-временным признакам и Multiple-Instance Learning, затем проверка порядка событий транзакции целиком. [Страница IBM](https://researcher.ibm.com/publications/detecting-sweethearting-in-retail-surveillance-videos). Коммерческие системы (AxxonSoft и др.) сверяют видео-события с данными POS; для настройки требуют дообучения под объект.
  - **Урок:** трёхступенчатая схема «дешёвые кандидаты → фильтр ложных → проверка порядка событий» совпадает с нашей двухстадийной политикой. Порядок событий («ушёл, значит должен был заблокировать») = наши omission-нарушения.
  - Поведенческие «подозрительные» признаки (частота общения с кассиром) критикуются за несправедливость и приватность; нам не нужны и лицам противоречат.
- **Mistake detection в процедурных видео** (Assembly101, EgoPER, CaptainCook4D и др.): PREGO ([arXiv 2404.01933](https://arxiv.org/abs/2404.01933)) делает онлайн-детекцию как one-class: распознанное действие сравнивается с предсказанным символьным модулем; [arXiv 2411.02570](https://arxiv.org/abs/2411.02570) использует LLM с chain-of-thought и in-context примерами для покадровых ошибок. По обзору в диссертации Тренто VLM плохо справляются с мелкой временной логикой, помогает перевод видео в последовательность шагов и проверка по автомату/HMM.
  - **Урок:** выделить небольшой **автомат состояний** сцены (кассир за столом / ушёл; сейф открыт / закрыт; экран заблокирован / нет) и проверять инварианты («при уходе: экран заблокирован, сейф закрыт, на столе нет ценностей»). Это лучше, чем просить VLM судить весь ролик.
- Кухонная гигиена, сборка на производстве: готовые SOP-системы обычно строятся на детекторе объектов и зонах (ROI) плюс правилах «объект X в зоне Y дольше N секунд». Для нас переносимо как детерминированный слой для объектов (телефон, стакан, сумка), но **зоны нельзя задавать пикселями из-за нового ракурса** (см. п. 4).

## 4. Как использовать 42 ролика

Ограничения: 22 нарушения с **одним** таймкодом, **типов нет**, дубли (Х-4/Х-47 один файл с двумя таймкодами, Х-5/Х-48 дубль), несколько ракурсов, видео 464×848.

1. **Группы для CV.** Склеить дубли по md5 в одну группу (в одной группе могут быть несколько таймкодов нарушений). Делить по группам, иначе утечка.
2. **Leave-one-angle-out.** Разметить ракурс каждого ролика (основной / повёрнутый стол, как Х-11 / с другой стороны, Х-30–Х-46). Обучать пороги на двух ракурсах, оценивать на третьем. Это честная оценка итога «новый ракурс» (10 баллов).
3. **Как пользоваться данными:**
   - *Калибровка порогов*: для каждого вопроса чек-листа собрать распределение ответа VLM в окнах вокруг меток нарушений против всех окон чистых роликов; подобрать порог так, чтобы recall по ролику был максимален при FP по чистым ≈ 0.
   - *Подбор промпта*: итерации вопросов по метрике LOO (в духе VERA); зафиксировать лучшие формулировки, потом **не трогать**, чтобы не переобучиться на 42 роликах. Хранить 6–8 роликов как «заморозку», смотреть на них только раз в конце.
   - *In-context примеры*: давать VLM 1–2 **кадра-эталона** («так выглядит заблокированный экран», «так выглядит ключ в замке») вместо видео. Видео в контексте дорогое и шумное; пары «кадр + ответ» дёшевы. Эталонные кадры нужны с разных ракурсов, иначе модель выучит ракурс.
   - *Нормальные примеры*: чистые ролики описывают «норму» (клиент входит, инкассатор передаёт, кассир уходит с заблокированным экраном). Это нужно явно вписать в промпт, чтобы не ловить норму за аномалию (идея индукции AnomalyRuler).
4. **Синтетика и аугментации (только для оценки/TTA, не для обучения):**
   - перспективные преобразования (±15–25°), поворот, зум/кроп 0.7–1.0, горизонтальное отражение, яркость/гамма, сжатие. Отражение безопасно, если в правилах нет «слева/справа».
   - Если запускать конвейер на 3–4 аугментированных копиях и голосовать, это **test-time augmentation**: повышает устойчивость и даёт оценку неопределённости. Дорого по времени, брать выборочно на спорных окнах.
   - Генерация видео диффузией для нарушений не стоит усилий за 24 ч.
5. **Свои ролики.** Организаторы разрешили. Записать телефоном 10–15 роликов по 15–40 с на другом ракурсе (сверху/сбоку/под острым углом): по 1 ролику на каждый тип из чек-листа, 3–4 чистых, 3–4 с типами, которых нет в обучении (например: камера/гаджет, посторонний предмет, не тот порядок пересчёта). Использовать как отдельный тест, **не** смешивать с калибровкой. Лица статистов не хранить в репозитории.
6. **Таймкоды обучения.** Измерить систематическое смещение между нашим детектором события и меткой (метка может быть на входе кассира, как у Х-33, или на уходе, как у Х-11/Х-28). Если смещение устойчиво — использовать как поправку по типу.

## 5. Политика решения при «промах недопустим, FP минимальны»

Два канала ошибок с разной ценой. Вердикт весит 25 баллов; точные веса промаха и FP неизвестны. Заложить асимметрию заранее, например `cost_miss = 3 × cost_FP`, и **оптимизировать ожидаемую стоимость на LOO**, а не точность.

1. **Порог по ролику = максимум по окнам.** Ролик «нарушение», если хотя бы одно окно превысило порог своего вопроса. Порог выбирать из условия recall = 100% на обучающих нарушениях с запасом (взять порог чуть ниже минимума среди положительных, затем проверить число FP на чистых). Для строгой гарантии можно использовать подходы вроде conformal / Learn-then-Test ([Angelopoulos и др., arXiv 2110.01052](https://arxiv.org/abs/2110.01052), по памяти) — на 22 положительных примерах доверительные интервалы широкие, честно писать это в отчёте.
2. **Двухстадийная проверка.** Стадия 1 (рекал): мягкий порог, много кандидатов. Стадия 2 (точность): для каждого кандидата **другой** запрос (другой кроп, другая формулировка, возможно другая модель) должен подтвердить минимум в 2 соседних кадрах. Подтверждённый → `violation`, неподтверждённый с высоким рейтингом стадии 1 → `needs_review`.
3. **Самосогласованность.** 3 прохода с разными кропами/сидом/аугментацией; требовать согласия ≥2/3. Температура 0 для основных запросов.
4. **Ансамбль.** Две VLM из разных семейств + детерминированный детектор объекта. Решение «да» — когда согласны минимум два источника для объектных нарушений (телефон, еда), либо VLM + правило автомата для нарушений состояния.
5. **Что возвращать при неуверенности.** Предложение: `verdict = "violation"`, `confidence = "low"`, `type = "unknown_review_required"`, один кадр-кандидат и честное описание «сомнительный эпизод, нужна проверка оператором». Обоснование: промах «недопустим», а при низкой уверенности мы не придумываем тип и норматив. Если в оценке жюри ложная тревога на чистом ролике стоит дорого, поднять порог так, чтобы такое поведение срабатывало редко; проверить эту долю на 20 чистых.
6. **Чистый ролик.** Возвращать `no_violation` с пустым списком, но хранить в отладочном выводе топ-кандидатов с оценками (для UX и аудита).

## 6. Новые типы нарушений и борьба с галлюцинациями

**Открытый проход (рекал для неизвестных типов):**
1. Подать VLM 4–8 кадров вокруг каждого события-кандидата (не весь ролик) и промпт со структурой: «Вот правила работы кассира: [список 10–15 правил, включая общий пункт «любое иное нарушение режима»]. Перечисли только то, что **видно на кадрах**, и для каждого пункта укажи номер кадра и объект». Ответ — строгий JSON по схеме (grammar-constrained decoding в vLLM / llama.cpp).
2. **Верификатор** (отдельный запрос, чистый контекст, другой кроп): «На кадре N есть ли X? Ответь yes/no». Без подтверждения пункт отбрасывается.
3. Отбрасывать пункты без указания кадра/объекта и пункты, противоречащие списку «нормы» (вход клиента, передача сумки инкассатором, уход кассира с заблокированным экраном).

**Антигаллюцинационные приёмы:** вопросы закрытые и бинарные, а не «опиши»; требовать цитату видимого признака; сначала описание кадра нейтральным промптом («что лежит на столе, что на экране»), затем применение правила к этому описанию (двухшаговое, как LAVAD) — так модель не подгоняет описание под ожидаемое нарушение; логиты вместо слов «уверен»; детектор объекта как независимое подтверждение; запрет типа/норматива из свободного текста — только из справочника, для неизвестного типа норматив «общий пункт о соблюдении режима» с пометкой `review`.

**Новый ракурс:** формулировки без слов «слева/справа/позади стола» (кроме «за кассиром» там, где это инвариантно); кропы привязывать к объектам (ноутбук, сейф, стол), а не к координатам кадра, находя их детектором открытого словаря. Это снимает главную зависимость от пикселей, отмеченную в `violation_hypotheses.md`.

## 7. Таймкод и кадры-доказательства

Метрика 15 баллов: допуск неизвестен, поэтому цель — точность ≤1–2 с.

| Класс нарушения | Какой момент считать таймкодом | Кадры (1–3) |
|---|---|---|
| **Присутствие** (телефон в руке, еда, посторонний, личные вещи) | **Начало (onset)**: первый кадр, где признак устойчиво виден (≥2 подряд) | onset; середина/пик, где признак виден лучше всего; при необходимости кадр «контекст» |
| **Опущение** (уход без блокировки, ключ в сейфе, ценности на столе) | **Момент ухода** кассира из зоны стола (последний кадр присутствия или первый без него; сверить с меткой обучения, где известно, как у Х-11, Х-28, Х-15) | кадр «до ухода» (кассир у стола), кадр «после» (пустой стол с открытым экраном/ключом/ценностями). Для ключа и экрана брать увеличенный кроп |
| **Посторонний** | Момент пересечения границы кассовой зоны / появления второго человека за кассиром | вход, пик (посторонний за спиной), уход |
| **Порядок приёма сумки** | Момент ухода инкассатора до завершения приёма | кадр передачи, кадр ухода |

Выбор лучшего кадра: чёткость (дисперсия Лапласиана), отсутствие перекрытия объекта рукой, максимальная оценка VLM, не ближе 0.5 с к другому выбранному. Всегда размывать лица перед записью файла. Кадры сохранять с подписью `t=…с` — для UX и проверки жюри.

Таймкод считать **своим детектором событий**, а не по словам VLM (см. п. 2.1). Уточнение: метка в обучении может быть ранней (Х-33: на входе кассира, хотя посторонний входит позже) — это прямой аргумент измерить смещение по обучающим парам.

## 8. Харнесс оценки (метрики как у жюри)

Данные: метки вердикта и один таймкод на ролик, типов нет. Для типа использовать **наши гипотезы** из `violation_hypotheses.md` как шумные псевдометки (в отчёте указывать это).

Структура: `eval/run_loo.py` читает кэшированные ответы модели (по хэшу кадра и версии промпта), считает метрики по группам.

| Метрика | Как считать | Соответствие критерию |
|---|---|---|
| **Вердикт** | recall по нарушениям (главная), FP-rate по чистым, итог = `25 · (1 − (3·miss + FP)/N)` при выбранной асимметрии; всегда показывать матрицу ошибок | 25 баллов |
| **Таймкод** | доля нарушений, где |t_pred − t_label| ≤ τ для τ = 1, 2, 3, 5 с (допуск жюри неизвестен); для роликов с несколькими нарушениями — венгерское сопоставление | 15 |
| **Кадры** | доля роликов, где хотя бы один выданный кадр в ±2 с от метки; дополнительно визуальная проверка 10 случайных | 15 |
| **Тип** | accuracy и macro-F1 по псевдометкам (9 предварительных классов); отдельно доля «unknown» | 15 |
| **Норматив** | детерминированно: тип → пункт по справочнику; проверка, что для каждого типа есть ровно один корректный пункт; ручной аудит описаний | 15 |
| **Ракурс** | те же метрики на сложении по ракурсам (leave-one-angle-out) + на аугментированных копиях + на своих роликах; разность с внутриракурсным результатом | 10 |
| **Техническое** | время обработки на ролик, пиковая память, воспроизводимость (seed, версия) | 10 |

Требования к харнессу: фиксированные группы по md5, **заморозка** 6–8 роликов, бутстреп-интервал по роликам (при N=42 разброс огромный: 1 ролик ≈ 2.4% точности), журнал ошибок с кадрами для разбора, регрессионный тест «чистые не должны давать нарушений». Переименовать файлы: латинская X и кириллическая Х в названиях — нормализовать.

## 9. Риски и что не делать

- Не доверять VLM таймкод и счёт секунд (п. 2.1).
- Не подгонять 40 порогов под 42 роликов без заморозки: переобучение на малой выборке гарантированно.
- Не вызывать облачные API даже «для проверки»: дисквалификация по условиям.
- Не строить правила на координатах кадра, не использовать эмбеддинги лиц, не сохранять неразмытые лица в выходных данных.
- Не выдумывать пункты норматива: только справочник.
- Х-44 и Х-32 в гипотезах не определены; не включать их в калибровку как положительные для конкретного типа, использовать только для вердикта.
