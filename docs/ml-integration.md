## Что есть в ветке ML

- FFmpeg-декодирование, оценка движения и выбор до 160 кадров.
- OpenAI-совместимый клиент VLM, извлечение 11 признаков состояния сцены,
  временная шкала и 8 правил состояния.
- Проверка трёх процедур: документ клиента, проверка банкнот, приём сумки;
  дополнительный поиск событий и повторная проверка кандидатов по кадрам.
- Каталог из 12 типов, 1–3 JPEG-доказательства, `to_jury` и `to_details`.
- Eval по XLSX: чтение разметки, объединение дубликатов, метрики классификации,
  попадания во время события и длительности; скрипты для Kaggle.

Это VLM-конвейер с правилами. Наличие модулей и тестов не подтверждает
качество детекции, нормативную корректность или скорость на целевом GPU.
Опубликованных результатов реального прогона в этой ревизии нет.

## Исправления при подключении

- Ленивый экспорт `ml.analyze`: API и `ml.stub` работают без ML-зависимостей.
  `stub` Docker-образ остаётся минимальным, `gpu` устанавливает зависимости ML.
- Пути `FFMPEG_BIN` и `FFPROBE_BIN` передаются из настроек бэкенда в runner
  и учитываются декодером ML. Подпроцессы имеют таймауты и работают с локальными файлами.
- Ошибки VLM, неверный JSON и неполное покрытие кадров помечают анализ `degraded`.
  Пропуск дополнительного поиска по бюджету также помечает результат неполным.
  Бэкенд отклоняет любой `degraded=True` как `failed`: частичный вывод нельзя
  выдавать жюри как завершённый результат без оговорки.
- VLM-ответы проверяются по JSON Schema. HTTP-клиент не использует прокси
  из окружения и не следует перенаправлениям с адреса выбранного сервера.
- Исправлена обратная полярность проверки двух процедур: ответ «да, документ /
  банкноты проверены» теперь исключает событие «проверка пропущена».
- Норматив без необязательных `point` и `quote` сериализуется корректно;
  ссылка на источник включается также в текст для жюри.
- Eval учитывает `degraded` как ошибку и не засчитывает ошибки на чистых видео
  как верные отрицательные ответы; отчёты явно сохраняются в UTF-8.
- `runs/` с результатами eval исключён из Docker-контекста, как и из Git.

## Локальная проверка

`tests/test_ml_integration.py` запускает весь путь: загрузка MOV → очередь →
отдельный runner → `ml.analyze` → локальный HTTP-сервер с протоколом VLM →
валидация обоих ответов → SQLite → защищённое MP4-превью с Range.
Ответы VLM заданы тестом; изображения не анализируются настоящей нейросетью.

Сценарии: чистое видео, событие с телефоном, HTTP 503, неверная схема JSON,
сбой только процедурного этапа, сбой верификации уже найденного события.
После ошибок проверяется успешная обработка следующей задачи тем же worker.
Дополнительные тесты проверяют полярность процедур, nullable-поля норматива,
валидацию VLM и запрет HTTP-redirect.

## Включение с готовым собственным VLM

```powershell
python -m pip --python .venv/Scripts/python.exe install -r requirements-ml.txt -c requirements.txt
$env:ANALYZER = 'ml:analyze'
$env:VLM_BASE_URL = 'http://localhost:8001/v1'
$env:VLM_MODEL = 'Qwen/Qwen3-VL-8B-Instruct'
# API_KEY и пути FFmpeg/FFprobe задаются как в основном README.
.venv/Scripts/python.exe -m uvicorn backend.app.main:create_app --factory --host 127.0.0.1 --port 8000
```

Конфигурацию модели и запуск локальных весов описывает `deploy/README.md`.
Не переключать рабочий сервис до готовности VLM. Наличие `mode=pipeline` в
`/health` показывает выбранный анализатор, а не подтверждает качество модели.

## Что остаётся до реальной готовности

1. Финальный выбор 8B/4B и ревизии весов после спайка; проверка версии vLLM,
   VRAM и обработки до 4 изображений в текущих ML-запросах (лимит сервера — 6).
2. Реальные прогоны MOV из датасета с метриками и проверкой ложных срабатываний.
   Eval уже исключает ошибочное засчитывание `degraded` как правильного ответа.
3. Измерение бюджета 240 с ML / 280 с обработки и полного времени с очередью:
   три backend-worker могут одновременно создавать до 24 запросов VLM.
   Внутренний бюджет ML не прерывает уже выполняющийся этап; общий таймаут
   бэкенда остаётся жёстким и убивает всё дерево процессов.
4. Ручная сверка нормативов и их применимости к событиям. У трёх типов
   (`eating_drinking`, `id_check_skipped`, `other_security_risk`) `rule=null`.
   Флаги `verified` в каталоге — данные ML-ветки, не результат новой юридической проверки.
5. GPU-сборка и офлайн-прогон с локальными весами; реальный фронтенд и Safari.

Существующие доказательства офлайн-работы CPU-заглушки не заменяют пункт 5.
