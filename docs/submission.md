# Observer — материалы сдачи

Статус: черновик. Бэкенд работает с демонстрационным анализатором; публичный
сервис и качество реального детектора ещё не подтверждены.

## Доступ

| Поле | Значение |
|---|---|
| Публичный UI | Не развёрнут — заполнить после RunPod |
| Базовый API URL | `<публичный URL>/api/v1` |
| Документация API | `<публичный URL>/docs` |
| API-ключ жюри | Передать отдельно; значение переменной `API_KEY` |
| Docker image + digest | Заполнить после сборки и проверки на GPU |
| Модель / ревизия весов | По умолчанию Qwen/Qwen3-VL-8B-Instruct; резерв Qwen/Qwen3-VL-4B-Instruct; финальная ревизия после Kaggle-спайка |

Запуск и curl: [README](../README.md). Инструкция GPU/RunPod:
[deploy/README.md](../deploy/README.md).

## Что реализовано в бэкенде

- Приём MOV/MP4 до 200 МиБ, проверка видеопотока через ffprobe.
- Защита `/api/*` ключом `X-API-Key`.
- Постоянное хранилище SQLite WAL; очередь из трёх процессов обработки,
  прогресс, восстановление незавершённых задач, таймаут 280 секунд.
- h264 MP4-превью с faststart и Range, раздача сборки фронта.
- Закрытый доступ к превью: cookie на одно видео на 15 минут, HttpOnly/SameSite,
  Secure на HTTPS; авторизованный `/details` обновляет доступ, URL без cookie даёт 401.
- Отдельные ответы жюри и UI, health-check GPU/vLLM/диска.
- Скрипты нагрузки и запуска контейнера без внешней сети.

## ML, нормативы и лицензии

**Модель.** Одна локальная VLM: [`QuantTrio/Qwen3-VL-30B-A3B-Instruct-AWQ`](https://huggingface.co/QuantTrio/Qwen3-VL-30B-A3B-Instruct-AWQ)
(AWQ-квантизация Qwen3-VL-30B-A3B, Apache-2.0) в vLLM 0.11.0 (Apache-2.0), `HF_HUB_OFFLINE=1`.
Видео, кадры и их описания не покидают сервер. Распознавание лиц не используется.

**Пайплайн** (`ml/pipeline.py`):

1. Декодирование FFmpeg, адаптивная выборка до 160 кадров (чаще там, где есть движение),
   контроль качества кадра: темнота, засвет, скачок экспозиции, замороженный поток.
2. Покадровый «сенсор»: VLM возвращает JSON-состояние сцены по строгой схеме
   (кассир на месте, деньги, сумка, сейф и т. д.). Кадры обходятся от грубой сетки к мелкой,
   и сенсор останавливается по дедлайну, поэтому ответ приходит даже под нагрузкой.
3. Сглаживание во временные интервалы и декларативные правила (`ml/rules.py`, `ml/catalog.yaml`).
4. Проверки на уходах кассира по увеличенному фрагменту: VLM находит ноутбук на кадре
   (grounding) и классифицирует экран (документ / экран блокировки / чёрный / закрыт),
   затем осматривает стол (деньги, сумка инкассации, личные вещи) (`ml/screen.py`).
5. Посторонний в зоне кассира: окна по 4 кадра каждые 2 с, нужны два соседних окна с ответом
   «да» (`ml/outsider.py`).
6. Верификация кандидатов отдельным вопросом VLM, кадры-доказательства (1–3 JPEG), таймкод
   и описание с нормой.

**Типы нарушений, которые сервис сообщает:**

| type_id | Что видно | Норма |
|---|---|---|
| workstation_unlocked | кассир ушёл, на экране открыт документ или таблица | Пост. АРРФР № 53, п. 71 пп. 9) |
| cash_unattended | кассир ушёл, на столе деньги или сумка инкассации | Пост. НБРК № 231, п. 20 ч. 2 |
| personal_items | личные вещи на рабочем столе кассира | Пост. НБРК № 231, п. 12 ч. 1 |
| eating_drinking | кассир ест или пьёт на рабочем месте | Пост. НБРК № 231, п. 12 ч. 1–2 (личные вещи вне кассового узла) |
| outsider_cashier_zone | посторонний на стороне кассира | Пост. НБРК № 14, п. 8 |
| safe_unsecured | кассир ушёл, сейф открыт | Пост. НБРК № 231, п. 20 ч. 2, п. 80 |

Все ссылки — adilet.zan.kz, цитаты дословные, в каталоге показываются только нормы с `verified: true`.
Типы `phone_use`, `id_check_skipped`, `banknote_check_skipped`, `bag_acceptance_violation` описаны
в каталоге, но не сообщаются: на 40 видео они давали ложные срабатывания без верных находок.

**Метрики на открытом датасете** (40 уникальных видео, 21 с нарушением; `eval/run_eval.py`):

| Версия | Точность вердикта | Полнота | Ложные на чистых | Таймкод ±5 с |
|---|---|---|---|---|
| Покадровые правила (до доработки) | 47,5 % | 33 % | 37 % | 18 % |
| Текущая | 70 % | 43 % | 0 % | 32 % |

Метрики посчитаны на тех же видео, на которых подбирались вопросы и пороги, поэтому
на новых видео ожидаемо ниже.

**Известные ограничения и ошибки:**

- Ключ, оставленный в замке сейфа, при разрешении 464×848 не различим. Такие случаи пропускаются.
- Телефон в руках кассира по одиночным кадрам и окнам путается с купюрами, трубкой и телефоном клиента,
  поэтому тип отключён.
- Пропускается посторонний, который подходит к счётной машине с клиентской стороны стола.
  Ловится тот, кто заходит на сторону кассира.
- Нарушения «по бездействию» (не проверил документ, не проверил купюры на детекторе) не сообщаются.
- Таймкод — начало интервала. Для ухода кассира это момент ухода, а не момент, когда нарушение стало видно.
- Нагрузка: шесть видео по 42–143 с, отправленные одновременно, завершаются за 249–269 с.
  Сенсор при этом урезается по дедлайну, и полнота ниже, чем при последовательной обработке.

## Ограничения и результаты приёмки

Локально проверено 17.10.2026 на Windows / Python 3.13.2 / FFmpeg 9.0.2:
Первый набор из 12 интеграционных проверок прошёл после адаптации к контракту ветки `ml`.
Проверены авторизация, загрузка, совместимость моков, точный ответ жюри,
JPEG, Range, три параллельных воркера, таймаут с завершением дочерних процессов,
восстановление после штатной остановки и аварийного завершения HTTP-сервера,
блокировка второго владельца очереди, HEVC/MOV → H.264/yuv420p/faststart.
Дополнительно проверены бюджет ML 240 секунд и его уменьшение при коротком общем
таймауте, передача VLM-переменных, методы сериализации внешнего результата и `degraded`.
Настоящие сериализаторы `ml/types.py` из `origin/ml` на ревизии
`ce05be8e498053cb62830983c6dc6db8419e44ec` отдельно проверены для чистого результата
и результата с нарушением. 18.10.2026 настоящий ML-пайплайн на GPU (RunPod) прошёл нагрузочный тест `deploy/loadtest.py`: шесть видео по 42–143 с одновременно, все `done` за 249–269 с.
Нагрузка через настоящий HTTP-сервер: шесть запросов с синтетическим односекундным
видео на заглушке завершились за 6,4–12,8 с от начала загрузки.
Проверка зависимостей `pip check` и синтаксиса shell-скриптов прошла.

Расширенная приёмка B1/B3/B6 и оставшиеся зависимости описаны в
[протоколе](backend-acceptance.md). Чистое Python-окружение устанавливается
из `requirements.txt`; `pip check` не обнаружил конфликтов. Этот запуск проверен
агентом, а самостоятельный запуск посторонним участником пока не подтверждён.

Контейнерная проверка CPU-заглушки проведена 17.10.2026: образ собран, запущен
с `--network none` и `--pull never`; реальный MOV 28,72 МБ прошёл HTTP-приёмку за
14,337 с, шесть одновременных загрузок — за 20,999–43,663 с. Результаты сохранились
после рестарта; внутри только loopback, внешнее TCP-соединение недоступно.
Image ID, окружение и отчёты указаны в [протоколе](backend-acceptance.md).
Docker Desktop сейчас работает; прежний блокер для CPU-проверки снят.
Целевая конфигурация GPU 24 ГБ и RunPod недоступны; локально определяется RTX 3060
Laptop 6 ГБ, VLM не запущен. Публичный URL, время восстановления ≤15 минут и offline
реального ML остаются критериями приёмки, которые ещё необходимо подтвердить.

- Фронтенд разрабатывается отдельно; без `frontend/dist` показывается только страница API.
- Ссылки на превью требуют cookie либо X-API-Key; после 15 минут нужно обновить `/details`.
- Автоматического удаления видео и БД нет; нужен контроль свободного места.
- Производительность заглушки не оценивает производительность ML.
- Целевой GPU, публичный HTTPS, Safari на роликах датасета и offline реального ML
  требуют проверки на целевом окружении.
- Итог анализа предназначен для проверки человеком.
