# Observer — материалы сдачи

Observer — локальный AI-сервис, который по видеозаписи кассы находит визуальные признаки
возможных нарушений кассовой дисциплины. Он показывает тип, таймкод, кадры-доказательства
и норму права РК. Результат — подсказка проверяющему, а не юридическое заключение.

## Использование

1. Откройте UI и загрузите `.mov` (до 200 МиБ). Ключ в интерфейсе не нужен: он ходит в служебные маршруты `/ui/v1`, а API жюри `/api/v1` защищён ключом.
2. Экран показывает этапы обработки. Короткое видео обрабатывается примерно за 30–90 с,
   шесть длинных одновременно — до 210 с.
3. Результат — «Нарушение не обнаружено» или «Обнаружены признаки возможных нарушений».
   Для каждого нарушения показаны тип, таймкод, 1–3 кадра, описание увиденного и норма
   (документ, пункт, цитата, ссылка на adilet). Клик по таймкоду переводит плеер к моменту события.
4. Если часть кадров не удалось проанализировать (плохой кадр, нехватка времени), результат
   помечается как требующий ручной проверки. Вердикт при этом всё равно выдаётся.

## Запуск

- **RunPod (текущий стенд):** `bash /workspace/start_all.sh` поднимает vLLM в офлайн-режиме и API.
  Скрипт идемпотентен и восстанавливает окружение после остановки пода; источник — `deploy/pod/start_all.sh`.
  Переменные сервиса лежат в `/workspace/api.env`.
- **Docker / другой GPU-сервер:** [deploy/README.md](../deploy/README.md).
- После загрузки весов интернет не нужен (`HF_HUB_OFFLINE=1`): vLLM на стенде перезапускался
  в офлайн-режиме. Если веса скачаны по конкретной ревизии, в кэше Hugging Face нужен файл
  `refs/main` с этой ревизией, иначе офлайн-запуск не найдёт модель.

## Архитектура

- **Фронтенд:** React 18 + TypeScript + Vite + Tailwind + shadcn/ui. Собирается в статику и
  раздаётся бэкендом, CDN не используются.
- **Бэкенд:** FastAPI, очередь в SQLite (WAL), 6 воркеров. API жюри `/api/v1` под ключом,
  те же обработчики для интерфейса — `/ui/v1` без ключа и вне публичной схемы. Каждая задача анализируется в
  отдельном процессе с бюджетом 280 с от момента загрузки. Есть h264-превью, закрытый доступ
  к медиа по cookie, `/health`.
- **ML:** `ml/` — одна локальная VLM через OpenAI-совместимый vLLM, подробно ниже.
- **Оценка качества:** `eval/run_eval.py` считает метрики на размеченных видео и умеет
  повторять прогон по кэшу ответов VLM без GPU.

## Нормативные источники и сопоставление с видео

Использованы только акты РК с adilet.zan.kz:

- [Постановление Правления НБРК от 29.11.2019 № 231](https://adilet.zan.kz/rus/docs/V1900019680)
  (правила кассовых операций): хранение наличных, сейфы и ключи, личные вещи и средства связи
  в кассовом узле, идентификация клиента, проверка подлинности банкнот на оборудовании, приём сумок инкассации.
- [Постановление Правления НБРК от 24.02.2020 № 14](https://adilet.zan.kz/rus/docs/V2000020075)
  (охрана и устройство помещений банков): изоляция кассового узла и закрывающийся вход.
- [Постановление Правления АРРФР от 03.04.2026 № 53](https://adilet.zan.kz/rus/docs/V2600038336)
  (требования к информационной безопасности): блокировка рабочей станции.

Принцип сопоставления: каждый тип нарушения в `ml/catalog.yaml` хранит наблюдаемый признак,
вопрос-проверку для VLM и норму (документ, пункт, дословная цитата, URL, флаг `verified`).
Сервис сообщает только то, что видно на кадрах. Нарушения, для которых нужны невидимые данные
(проводки, сверки, журналы), не утверждаются. Цитаты сверены с текстом на adilet.

## ML, нормативы и лицензии

**Модель.** Одна локальная VLM: [`QuantTrio/Qwen3-VL-30B-A3B-Instruct-AWQ`](https://huggingface.co/QuantTrio/Qwen3-VL-30B-A3B-Instruct-AWQ)
(AWQ-квантизация Qwen3-VL-30B-A3B, Apache-2.0) в vLLM 0.11.0 (Apache-2.0), `HF_HUB_OFFLINE=1`.
Видео, кадры и их описания не покидают сервер. Распознавание лиц не используется.

**Пайплайн** (`ml/pipeline.py`):

1. Декодирование FFmpeg, адаптивная выборка до 160 кадров (чаще там, где есть движение),
   контроль качества кадра: темнота, засвет, скачок экспозиции, замороженный поток.
2. Покадровый «сенсор»: VLM возвращает JSON-состояние сцены по строгой схеме
   (кассир на месте, деньги, сумка, сейф и т. д.). Кадры обходятся от грубой сетки к мелкой,
   и сенсор останавливается по дедлайну, поэтому ответ приходит даже под нагрузкой.
3. Сглаживание во временные интервалы и декларативные правила (`ml/rules.py`, `ml/catalog.yaml`).
4. Проверки на уходах кассира по увеличенному фрагменту: VLM находит ноутбук на кадре
   (grounding) и классифицирует экран (документ / экран блокировки / чёрный / закрыт),
   затем осматривает стол (деньги, сумка инкассации, личные вещи) (`ml/screen.py`).
5. Действия по окнам из 4 кадров каждые 2 с (`ml/actions.py`): VLM заполняет анкету —
   пересчёт руками, счётная машина, дверь открыта, инкассатор, сумка и др. Правила: дверь открыта
   три окна подряд (~6 с); купюры пересчитаны руками, а счётная машина за ролик не использовалась.
6. Посторонний в зоне кассира: окна по 4 кадра, нужны два соседних окна с ответом «да» (`ml/outsider.py`).
7. Под нагрузкой проверки идут в порядке пользы, а сенсор получает не больше 37,5 % бюджета:
   ответ приходит до дедлайна, и самые результативные проверки не срезаются.
8. Верификация кандидатов отдельным вопросом VLM, кадры-доказательства (1–3 JPEG), таймкод
   и описание с нормой.

**Типы нарушений, которые сервис сообщает:**

| type_id | Что видно | Норма |
|---|---|---|
| workstation_unlocked | кассир ушёл, на экране открыт документ или таблица | Пост. АРРФР № 53, п. 71 пп. 9) |
| cash_unattended | кассир ушёл, на столе деньги или сумка инкассации | Пост. НБРК № 231, п. 20 ч. 2 |
| personal_items | личные вещи на рабочем столе кассира | Пост. НБРК № 231, п. 12 ч. 1 |
| eating_drinking | кассир ест или пьёт на рабочем месте | Пост. НБРК № 231, п. 12 ч. 1–2 (личные вещи вне кассового узла) |
| outsider_cashier_zone | посторонний на стороне кассира | Пост. НБРК № 14, п. 8 |
| safe_unsecured | кассир ушёл, сейф открыт | Пост. НБРК № 231, п. 20 ч. 2, п. 80 |
| door_left_open | дверь кассового помещения открыта ~6 с подряд | Пост. НБРК № 14, п. 8 |
| banknote_check_skipped | купюры пересчитаны руками, счётная машина не использовалась | Пост. НБРК № 231, п. 41, п. 9 |

Все ссылки — adilet.zan.kz, цитаты дословные, в каталоге показываются только нормы с `verified: true`.
Типы `phone_use`, `id_check_skipped`, `bag_acceptance_violation` описаны в каталоге, но не сообщаются:
на 40 видео они давали ложные срабатывания без верных находок.

**Метрики на открытом датасете** (40 уникальных видео, 21 с нарушением; `eval/run_eval.py`):

| Версия | Точность вердикта | Полнота | Ложные на чистых | Таймкод ±5 с |
|---|---|---|---|---|
| Покадровые правила (до доработки) | 47,5 % | 33 % | 37 % | 18 % |
| Крупный план экрана и стола, только точные проверки | 70 % | 43 % | 0 % | 32 % |
| **Текущая: + проверки действий (дверь, пересчёт)** | **72,5 %** | **76 %** | 32 % | 45 % |

Приоритет по FAQ кейса (п. 16): пропуск нарушения недопустим, ложных тревог — как можно меньше.
Поэтому текущая версия находит 16 из 21 нарушения ценой тревоги на 6 из 19 чистых видео.
Прогон шёл в 4 потока: в среднем 35 с на видео, максимум 116 с. Между прогонами точность колеблется
в пределах 72,5–75 %: при параллельных запросах ответы модели не полностью детерминированы.
Метрики посчитаны на тех же видео, на которых подбирались вопросы и пороги, поэтому
на новых видео ожидаемо ниже.

**Известные ограничения и ошибки:**

- Ключ, оставленный в замке сейфа, при разрешении 464×848 не различим. Такие случаи пропускаются.
- Телефон в руках кассира по одиночным кадрам и окнам путается с купюрами, трубкой и телефоном клиента,
  поэтому тип отключён.
- Пропускается посторонний, который подходит к счётной машине с клиентской стороны стола.
  Ловится тот, кто заходит на сторону кассира.
- Проверка документа клиента «по бездействию» не сообщается. Пересчёт без счётной машины сообщается,
  но иногда срабатывает на чистых видео.
- Дверь: если она открыта только в начале ролика (кто-то вошёл), таймкод может указывать на начало видео.
- Таймкод — начало интервала. Для ухода кассира это момент ухода, а не момент, когда нарушение стало видно.
- Нагрузка: шесть видео по 42–143 с, отправленные одновременно, завершаются за 185–202 с.
  Анализ при этом урезается по дедлайну, часть второстепенных проверок может пропускаться.

сохранение результатов после рестарта (`deploy/offline-check.sh`, см. [deploy/README.md](../deploy/README.md)).

## Эксплуатационные ограничения

- Превью по ссылке требует cookie или `X-API-Key`; через 15 минут ссылку нужно обновить через `/details`.
- Видео и база не удаляются автоматически, нужен контроль свободного места.
- Итог анализа — подсказка для проверяющего, решение принимает человек.
