# Контракт интеграции backend и frontend

Реализовано в `dunan/backend-video-processing`. Сборка фронта ещё не опубликована;
совместная проверка F2/F3/F6 и подтверждение фронтендером остаются открытыми.
Имена полей ответа жюри и формат `preview_url` не менялись.

## Защищённый плеер

1. Загрузить видео и опрашивать `/api/v1/jobs/{id}/details` с `X-API-Key`.
2. Ответ `done` с `preview_url` выдаёт HttpOnly cookie `cashguard_preview`.
   Cookie подписана сервером, действует 900 секунд и только для конкретного
   `/previews/{id}.mp4`. Её нельзя использовать вместо ключа API.
3. Установить `<video src={details.preview_url}>` на том же origin.
   Браузер отправляет cookie сам, включая запросы Range при перемотке.
4. При истечении доступа повторить `/details` с ключом и перезагрузить video,
   сохранив `currentTime`. Не повторять это бесконечно при сетевой ошибке.
5. Если превью отсутствует или недоступно, оставить карточки и JPEG доказательств.

В production фронт лежит в `frontend/dist` и обслуживается тем же FastAPI.
На HTTPS cookie имеет `Secure`; за TLS-прокси дополнительно установить
`MEDIA_COOKIE_SECURE=1`. Ответы `/details`, `/jobs` и media имеют `Cache-Control: no-store`.
Основной API-ключ не включать в `preview_url`, query string или логи.
Доступ без cookie/заголовка возвращает `401`; отсутствующее видео с валидным ключом — `404`.

Для Vite рекомендуется proxy **обоих** префиксов, сохраняя относительные URL:

```ts
server: {
  proxy: {
    '/api': 'http://127.0.0.1:8000',
    '/previews': 'http://127.0.0.1:8000',
  },
}
```

Если API вызывается напрямую с другого порта, использовать `credentials: 'include'`
в fetch и `crossOrigin="use-credentials"` у video. Разрешены конкретные origin из
`CORS_ORIGINS`; backend возвращает `Access-Control-Allow-Credentials: true`.
Не смешивать `localhost` и `127.0.0.1`: SameSite cookie предназначена для одного сайта.
Для разных сайтов используйте общий proxy/origin, а не ослабляйте cookie.

## Ответы и нормативные источники

- `/jobs/{id}` в `done`: только `job_id`, `status`, `verdict`, `violations`.
  Каждое событие: `type`, `timecode_sec`, `description`, `evidence_frames`.
- `/details` добавляет прогресс, статистику, таймлайн, поля карточек, `degraded`.
  Совпадающие данные обеих проекций должны совпадать; противоречие переводит job в `failed`.
- `no_violation` означает пустой массив; `violation` требует хотя бы одно событие.
  Каждое событие содержит непустое объяснение и 1–3 декодируемых JPEG base64.
- `rule: null` обозначает отсутствие подтверждённой нормативной ссылки.
  UI должен явно показывать эту неполноту, а не создавать норматив самостоятельно.
- При наличии `rule` backend требует непустой `document` и абсолютный HTTP(S) `url`.
  `point` и `quote` допускают `null` либо отсутствие: FAQ31 разрешает источник без
  точного пункта. Пустые строки не считаются содержательными значениями.
  UI показывает документ/ссылку и только заполненные пункт/цитату.

Поддержка nullable `point`/`quote` добавлена на backend; `contracts.ts` и моки
фронтенда здесь не изменялись. Это описание реализации для совместной проверки,
а не подтверждение уже состоявшегося согласования. Нормативы и юридическую
корректность источников подтверждает команда, backend проверяет форму данных.

## Совместная проверка после публикации фронта

Открыть `/`, загрузить настоящий MOV, дождаться результата, сопоставить обе
проекции с карточками F2. Проверить 0/1/3+ событий, неизвестный `type_id`,
неполный норматив, `rule:null`, ошибку анализа. В Chrome и Safari проверить
воспроизведение, переход по таймкоду, истечение/обновление media cookie и сценарий
недоступного превью. Сохранить версии браузеров и ссылку на отчёт без секретов.
