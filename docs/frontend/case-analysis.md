Вердикты: «Нарушение не обнаружено» и «Обнаружены признаки возможных нарушений».
Ошибка обработки не означает отсутствие нарушения. Для каждого события нужен свой набор доказательств.
Кадр и подпись времени берутся из ответа сервера; frontend не придумывает описание или норматив.

Критерии жюри: обнаружение 25, локализация 15, классификация 15, правила 15,
устойчивость 10, продукт 10, техника 10 баллов (с.3).
UI представляет доказательства для оценки, но сам по себе не обеспечивает качество ML или юридическую корректность.

## 2. Где заканчивается кейс и начинаются решения команды

</div>

- **Кейс:** .mov около 29 МБ, минимум 40 обучающих роликов по 10–145 с, FPS от 29 (с.5–6).
  MP4 и максимум 200 МиБ — расширения проекта; это не лимиты организатора.
- **Пользователь:** название GuardTusk, React + Vite, shadcn/ui, минимальный UI в стиле Forte.
  TypeScript, русский язык, светлая тема и same-origin раздача FastAPI закреплены в брифе проекта.
  FAQ26 разрешает команде выбрать язык.
- **Команда:** `/details`, четыре этапа, polling 1,5 с, confidence, плеер, lightbox и дорожки.
  Плеер помогает проверить фрагмент, lightbox — рассмотреть кадр; отдельные дорожки не обязательны для сдачи.
- **Не добавляем:** историю, пользовательскую регистрацию/вход, экспорт и пакетную загрузку (FAQ27).
  Поле технического API-ключа остаётся, поскольку сам API обязан проверять `X-API-Key`.
- **Не обещаем без проверки:** анализ за 1–2 минуты, готовое размытие лиц или проверенные нормативы.
  Запрет идентификации лиц не равен требованию размытия; размытие — решение backend/ML.

## 3. Оговорки и границы контракта

</div>

1. **Два вердикта.** FAQ15 упоминает «Недостаточно данных», но §4–5 и схема §10 задают
   только `violation/no_violation`. Сохраняем два значения; неопределённость поясняем текстом,
   а `failed` оставляем техническим статусом. Третий verdict без уточнения организаторов не вводим.
2. **Источник без пункта.** §4 просит название и пункт/раздел, FAQ31 принимает ссылки без точного пункта
   и открытые документы других банков; FAQ30 сохраняет юрисдикцию РК.
   Показываем доступные реквизиты, не выдумываем пункт. Исследование и проверка нормы принадлежат ML/команде.
   `rule:null` можно корректно отобразить, но такая карточка не доказывает выполнение требования об источнике.
3. **Два API одного результата.** Обязательный `/api/v1/jobs/{id}` остаётся строго по схеме PDF.
   `/details` — принятое расширение для UI. Проверяем совпадение событий, времён и кадров обеих проекций,
   а не заменяем один endpoint другим. Нормативная связь в `description` ответа жюри — решение команды,
   потому что в его схеме нет отдельного `rule`. Nullable/отсутствующий пункт согласовать в B1 до правок типов/моков.
4. **Точное доказательство.** FAQ17 требует конкретный кадр и таймкод, числового допуска не задаёт.
   Внутренние ориентиры ±2 с для оценки ML или ±0,5 с для seek плеера не являются допуском жюри.
   Контекстное воспроизведение с −1 с не меняет время события или JPEG.
5. **Пять минут.** Таймер ожидания браузера не доказывает срок сервиса.
   Для приёмки команды измеряем путь от отправки до результата, включая очередь; начало измерения сохраняем
   при повторном polling. Лимит жюри — 5 минут; обещание обычной скорости требует реального замера.
6. **Локальность и публичность.** Публичный URL нужен для сдачи, возможность обработки без внешней сети —
   для переноса. В офлайн-проверке браузер должен сохранять доступ к локальному сервису.
   Текст источника читается в карточке; переход на нормативный сайт — явное действие пользователя.
7. **Доступ к preview.** `<video src>` не передаёт произвольный `X-API-Key`.
   B3 и frontend должны согласовать защищённую раздачу media до F3, без основного ключа в URL.

## 4. Что есть сейчас

</div>

Проверено по `frontend/src/App.tsx`, `useAnalysis.ts`, `api/client.ts`, `api/contracts.ts`,
`dev/demo-api.ts` и `docs/frontend/mock_details*.json`.

- Есть F1: выбор файла, XHR-загрузка, API-ключ, polling `/details`, статус/прогресс, ошибки и повтор.
  Текущий экран результата содержит общий вердикт, число событий, правил и время.
- **Нет обязательных карточек:** отдельные события, таймкоды, кадры, наблюдение, объяснение, источник ещё не выводятся.
  Плеер, lightbox и дорожки также не реализованы.
- Типы предусматривают данные F2, но runtime-проверка пока не гарантирует согласованность вердикта и массива событий,
  число/декодирование JPEG и непустое объяснение. Это добавлено в критерии F2/B1.
- Демо явно обозначено, возвращает фиксированный пример и не реализует обязательную проекцию `/jobs/{id}`.
  В моках есть повторяющиеся JPEG, пример нормативной цитаты и `rule:null`; это материал UI, не анализ нового видео.
- После доработки F1 общее время начинается до POST и сохраняется при повторе статуса.
  Retry продлевает только ожидание; неизвестный этап нейтрален, чужой job_id отклоняется.
  Суммарные 300 с реального сервиса не подтверждены. Backend/dataset/публичный URL не запускались.

F1 остаётся **In Review**. Ни одна задача не закрыта на основании демо или этого анализа.

## 6. Как должен выглядеть минимальный результат

</div>

Компактная шапка GuardTusk, заголовок «Проверка видео», одна колонка до 800 px.
Загрузка/ключ/прогресс сменяются вердиктом, карточками доказательств и кнопкой «Новое видео».
Если F3 включён, плеер располагается перед карточками. F4 появляется только после базовой приёмки.

Стиль [Forte](https://forte.kz/ru): Open Sans, фон `#F7F6F6`, белые карточки,
основная кнопка `#4A0221`, акценты `#A31551`, скругления 12 px у кнопок и 24–32 px у секций.
Используем существующие shadcn/ui-компоненты и токены `frontend/src/styles.css`.
Цвет дополняется текстом/иконкой. Декоративные секции, логотип банка и банковская навигация не нужны.

## 7. Порядок после ревью

</div>

1. Пользователь проверил разбор и разрешил продолжить. Подготовка F0 отмечена, доработки F1 локально проверены.
2. Дорабатываем и принимаем F1 → F2, затем проверяем весь обязательный сценарий.
3. F5 проверяет доступность, адаптив и стиль; F6 — реальный сервис и условия сдачи.
4. F3 можно вести после F2 при готовности B3; если он включён, его также проверяем в F5/F6.
5. F4 выполняем при оставшемся времени после F6 и наличии реального timeline.

Контрольные точки: после F2 — 0/1/3+ событий и доказательства; после F5/F6 — публичный
сценарий и переносимость без внешней сети. Время сдачи 12:00 дано в FAQ33,
дата 18.10 и промежуточный фриз 11:00 — план проекта, а не дата из PDF.
Локальные и браузерные проверки записаны в `docs/frontend/acceptance.md`; открытые пункты F6
дополняем после живой приёмки. Мок-JSON и wire contract сохранены; runtime F1 доработан по этому плану.
