## 0. Цель и критерии успеха

Сервис принимает `.mov`, за ≤ 5 мин возвращает вердикт и список нарушений:
тип, таймкод, 1–3 кадра, описание, норматив РК. Есть UI и API для жюри.

| Критерий жюри | Баллы | Чем отвечаем |
|---|---|---|
| Вердикт на видео | 25 | Высокий recall (пропуск недопустим) + верификатор против ложных срабатываний |
| Таймкод и кадр | 15 | Таймкод из трекера состояний, а не из ответа VLM; кадр с рамкой на объекте |
| Тип | 15 | Закрытый каталог типов, тип = правило, которое сработало |
| Нормативы | 15 | Справочник «тип → пункт», модель ссылки не генерирует |
| Новый ракурс | 10 | Никаких пиксельных зон: раскладка сцены калибруется по каждому видео |
| Продукт | 10 | Надёжная загрузка, понятные карточки с доказательствами; плеер и дорожки — улучшения |
| Техника | 10 | Локально, офлайн-образ, лицензии Apache/MIT, оценщик на 42 роликах |

## 1. Ключевая идея

Анализ данных показал: датасет состоит из пар «чистый / нарушение», которые различаются **деталью состояния**
(экран не заблокирован, деньги на столе, ключ в сейфе) или **пропущенным шагом процедуры**
(нет проверки на детекторе, инкассатор ушёл до приёма). Сами действия «вошёл», «вышел», «передал» нормальны.

Поэтому система строится не как классификатор клипов, а как **цифровой протокол смены**:

1. Восстановить из видео **таймлайн состояний сцены**: кто где, что на столе, состояние ноутбука, сейфа и двери.
2. Восстановить **шаги процедур**: приём денег, пересчёт, проверка подлинности, приём сумки, уход с места.
3. Проверить таймлайн **декларативными правилами** (состояния) и **шаблонами процедур** (пропущенные шаги).
4. Каждого кандидата **верифицировать VLM** по кадрам окна, отдельно **открытым проходом** ловить неизвестные типы.
5. Собрать ответ: тип из каталога, таймкод события, кадр с рамкой, описание из фактов, пункт норматива.

Это даёт объяснимость («вот таймлайн, вот правило, вот пункт») и переносимость на новый ракурс и новые типы.

## 2. Архитектура

```

 браузер ──HTTP─▶ FastAPI (backend/)                                     │
 жюри   ──HTTP─▶  ├─ /api/v1/analyze, /api/v1/jobs/{id}, X-API-Key       │

                │  ├─ статика frontend/                                  │

                │        ├─ детектор/трекер (in-process, GPU)            │
                │        └─ HTTP → vLLM :8001 (Qwen3.5-9B / Qwen3-VL-8B) │
                └────────────────────────────────────────────────────────┘
```

Репозиторий:

```
backend/   API, очередь, хранение, превью видео        — бэк
frontend/  статика (стек и дизайн — docs/frontend/BRIEF.md)  — фронт

eval/      прогон на 42 роликах, метрики жюри            — ML
docs/      ТЗ-артефакты, исследования, спеки
```

Единственный стык ML и бэка:

```python
# ml/pipeline.py
def analyze(video_path: Path, deadline_s: float = 240.0,
            on_progress: Callable[[str, float], None] | None = None) -> AnalysisResult
```

`ml/stub.py` реализует ту же сигнатуру и возвращает фейковое нарушение с настоящим кадром,
чтобы фронт и бэк работали с первого часа.

## 3. ML-пайплайн

### 3.1 Декодирование и адаптивная выборка кадров

- `ffmpeg` → кадры с точными PTS. Базово **2 fps** для всего видео.
- Детектор движения (разность кадров) и смена числа людей → **уплотнение до 8 fps** в окнах ±2 с вокруг изменений.
- Для длинных видео (> 90 с) база 1 fps. Бюджет кадров для VLM ≤ 160 на видео.

### 3.2 Калибровка раскладки сцены (против нового ракурса)

По 3 кадрам из начала, середины и конца:
- детектор + OWLv2 находят **якоря**: стол, ноутбук, счётную машину, сейф, дверь, стулья;
- VLM один раз отвечает на вопрос о раскладке: с какой стороны стола сидит кассир, где клиентская сторона, где вход.

Из этого строятся зоны в координатах относительно стола: `cashier_side`, `client_side`, `doorway`, `safe_area`.
Зоны нормируются на размер стола, поэтому переносятся между ракурсами A–D и на новый.

### 3.3 Люди и роли (без лиц)

- Детектор людей **D-FINE-S** (COCO, Apache) на 5–8 fps + ByteTrack (`supervision`, MIT).
  Замер коллеги на T4: 0,036 с/кадр (≈10 с на видео 145 с при 2 fps), CPU 0,37 с/кадр. Запасной — RT-DETRv2-R18 (0,033 с).
  OWLv2 (0,38 с на T4, 6,9 с на CPU) — **только** для калибровки сцены по 3 кадрам, не на потоке.
  Grounding DINO tiny (0,52 с / 14,6 с) не используем.
- Роль по поведению, не по лицу:
  - **кассир** — трек с максимальным временем в `cashier_side` у ноутбука или стула;
  - **инкассатор** — трек, связанный с зелёной сумкой при входе;
  - **клиент** — трек, который сидит или стоит в `client_side`;
  - **посторонний** — любой не-кассир в `cashier_side` дольше 1,5 с.
- Лица на выходных кадрах размываем: распознавать запрещено, а размытие ещё и защищает данные.

### 3.4 Таймлайн состояний (VLM как сенсор)

На каждый выбранный кадр VLM получает полный кадр и 2× кроп стола и отдаёт JSON по фиксированной схеме
(guided decoding, `enable_thinking=false`):

```json
{
  "cashier_present": true,
  "cashier_holding": ["cash" | "phone" | "cup" | "food" | "document" | "bag" | "none"],
  "cashier_action": "sitting|standing|walking_away|counting_cash|using_machine|at_safe|drinking|eating|typing",
  "others": [{"zone": "client_side|cashier_side|doorway", "role_guess": "client|collector|staff|unknown", "holding": [...]}],
  "laptop": {"lid": "open|closed|not_visible", "screen": "app_unlocked|lock_screen|off|not_visible"},
  "safe":   {"door": "open|closed|unknown", "key_in_lock": "yes|no|unknown"},
  "desk_items": ["cash", "collection_bag", "personal_bag", "outerwear", "cup", "food", "tablet", "phone", "documents"],
  "door": "open|closed|unknown",
  "id_document_check": "yes|no|unknown",
  "banknote_check_device_used": "yes|no|unknown"
}
```

Результат по кадрам сглаживается (медиана по окну 1–1,5 с, гистерезис вкл/выкл, минимальная длительность)
и сливается с треками людей. Выход — таймлайн: интервалы для каждого признака.

Почему VLM, а не набор узких классификаторов: за 21 час один ML-инженер не обучит и не откалибрует
детекторы для экрана, ключа, сумки и купюр под 5+ ракурсов. VLM даёт все признаки сразу и переносится на новый ракурс.
Детектор остаётся для того, что VLM делает плохо: точное время входа и выхода, число людей, рамки.

### 3.5 Правила по состояниям (каталог `ml/catalog.yaml`)

Каждый тип — декларативное правило над таймлайном. Таймкод задаётся в правиле.

| type_id | Условие | Таймкод | Данные |
|---|---|---|---|
| `workstation_unlocked` | кассир ушёл (absent ≥ 3 с), а `screen = app_unlocked` в окне [уход, +5 с] | момент ухода | Х-11, Х-28 |
| `workstation_left_open` | кассир ушёл, ноутбук открыт с тёмным экраном, в норме этого же ракурса крышка закрыта или экран заблокирован | момент ухода | Х-13?, Х-15, Х-24 |
| `cash_unattended` | `cash` или `collection_bag` на столе при `cashier_present = false` ≥ 3 с **или** при входе другого человека, пока кассир не работает с этими деньгами | начало эпизода | Х-15, Х-26, Х-38, Х-4 |
| `safe_unsecured` | сейф открыт, а кассир не у сейфа ≥ 3 с, **или** `key_in_lock = yes` при уходе кассира | начало эпизода | Х-20, Х-22 |
| `personal_items` | `personal_bag` или `outerwear` на столе ≥ 3 с | начало | Х-40 |
| `eating_drinking` | `cashier_action ∈ {drinking, eating}` ≥ 1 с; чашка на столе сама по себе не нарушение (Х-25 чистый) | начало | Х-46 |
| `phone_use` | `phone ∈ cashier_holding` ≥ 2 с; телефон у клиента игнорируется | начало | тест |
| `outsider_cashier_zone` | не-кассир в `cashier_side` ≥ 1,5 с (кроме инкассатора в момент передачи у края стола) | вход в зону | Х-30, Х-18, Х-33 |
| `desk_not_cleared` | при уходе кассира на столе остаются ценности или рабочие предметы | момент ухода | Х-24 |

### 3.6 Шаблоны процедур (пропущенные шаги)

VLM размечает **шаги** по окнам 4 с (4 кадра): `client_hands_cash`, `id_check`, `count_by_hand`, `machine_count`,
`banknote_check_device`, `cash_to_safe`, `cash_to_client`, `bag_handover`, `bag_seal_check`, `collector_leaves`.

Шаблоны — упорядоченные последовательности с обязательными шагами:

| type_id | Процедура | Нарушение | Данные |
|---|---|---|---|
| `banknote_check_skipped` | приём наличных → пересчёт → **проверка подлинности** → сейф | нет проверки на детекторе | Х-44 (vs Х-43) |
| `id_check_skipped` | приём наличных → **проверка документа** → … | нет проверки документа (по закону обязательна всегда; Х-39 — ловушка разметки, со слов организаторов в чате) | Х-2 (vs Х-3) |
| `bag_acceptance_violation` | передача сумки → **проверка пломбы при инкассаторе** → уход инкассатора | инкассатор ушёл до приёма, сумка вскрыта без него | Х-17 (vs Х-16) |
| `count_out_of_view` | пересчёт над столом на виду у камеры и клиента | пересчёт у лица или вне кадра, выдача через стол | Х-1 (vs Х-3) |

Таймкод для пропуска — момент, когда шаг должен был произойти (следующий шаг процедуры).

### 3.7 Верификация кандидатов

Для каждого кандидата VLM получает 6 кадров окна [t−2, t+4] и кроп области,
плюс **вопрос конкретного правила** («Кассир ушёл. Экран ноутбука показывает открытое приложение, а не экран блокировки?»).
Ответ: `yes/no/unclear`, номер лучшего кадра, 1–2 предложения того, что видно.

- `yes` → подтверждено.
- `unclear` → три прогона (self-consistency), решает большинство.
- Уверенность = f(сила правила, logprob ответа, согласие прогонов).

### 3.8 Открытый проход (неизвестные типы)

Окна по 8 с, 4 кадра, вопрос: «Есть ли здесь нарушение кассовой дисциплины из списка [каталог] или другое явное
нарушение безопасности кассы? Ответь `none`, если ничего нет». Находки вне каталога проходят двойную верификацию
и выдаются как `other_security_risk` **без привязки к конкретному пункту**, если подходящего пункта нет:
описание говорит «требует проверки». Лучше честно, чем выдуманная ссылка.

### 3.9 Вердикт и калибровка

- `violation`, если есть хотя бы одно подтверждённое нарушение с уверенностью ≥ τ.
- τ подбирается на 42 роликах: 100% recall на обучающих нарушениях, затем минимум ложных срабатываний на чистых.
- Проверка переносимости: leave-one-angle-out (A, A2, B, C, D) и аугментации (перспектива, отражение, кроп, яркость).
- Дубли (Х-4 = Х-47, Х-5 = Х-48) склеиваются по md5, чтобы не завышать метрики.

### 3.10 Кадры-доказательства и описание

- 1–3 кадра: **начало** события, **пик**, **последствие** (например, пустая касса с открытой таблицей).
- На кадре рамка вокруг объекта (бокс от детектора или grounding VLM) и подпись типа. Лица размыты.
- Описание собирается из фактов таймлайна по шаблону, VLM только формулирует:
  «В 08,6 с кассир положила пачку купюр на стол и вышла из кассы; пачка остаётся на столе без присмотра 6 с.
  Это может указывать на нарушение порядка хранения наличных (Постановление НБРК № 231, п. 20)».
  Без утверждений, которые не видны на видео.

### 3.11 Бюджет времени (RTX 4090, оценка, замерить в спайке)

| Этап | Видео 145 с |
|---|---|
| Декод + выборка | ~5 с |
| Детектор D-FINE-S + трекер, 5 fps (замер T4: 0,036 с/кадр) | ~25 с на T4, ~10 с на 4090 |
| OWLv2, калибровка по 3 кадрам | ~1 с |
| VLM-сенсор, ~160 кадров батчем | ~40–60 с |
| Шаги процедур, ~36 окон | ~15 с |
| Верификация, ~10–20 кандидатов | ~10–20 с |
| Открытый проход, ~18 окон | ~10 с |
| **Итого** | **~90–120 с** |

Деградация по дедлайну: если до `deadline_s` остаётся < 40 с, пропускаем открытый проход,
затем self-consistency, и отдаём `done` с тем, что уже подтверждено.

## 4. Каталог нарушений и нормативы

`ml/catalog.yaml` — единый источник правды для типов, правил, текстов и нормативов:

```yaml
- type_id: cash_unattended
  title_ru: Наличные или ценности оставлены без присмотра
  rule: {...}                # условие над таймлайном
  verify_question: "..."     # вопрос верификатору
  norm:
    document: "Постановление Правления НБРК от 29.11.2019 № 231"
    point: "п. 20"
    quote: "..."
    url: "https://adilet.zan.kz/rus/docs/V1900019680"
    verified: true
```

Нормативы берём только из `docs/research/01_normative_base.md` с пометкой VERIFIED.
Перед сдачей каждый пункт сверяем вручную в браузере на adilet.
Пробелы (еда, посторонние, блокировка экрана) закрываем вторым заходом по источникам или формулируем как
«косвенно следует из п. …».

## 5. API и контракт

Решение: в ответе жюри **только поля из ТЗ**, без своих ключей. Норматив входит в текст `description`,
чтобы сохранить нормативную связь в заданной схеме; отдельного поля источника в PDF нет.
Это способ представления команды, а не подтверждение внутренней методики автоматического оценщика.

```json
{
  "job_id": "3f2a9c1e", "status": "done", "verdict": "violation",
  "violations": [{
    "type": "Наличные или ценности оставлены без присмотра",
    "timecode_sec": 8.6,
    "description": "В 8,6 с кассир положила пачку купюр на стол и вышла из кассы; пачка остаётся без присмотра 6 с. Может указывать на нарушение порядка хранения наличных. Норматив: Постановление Правления НБРК от 29.11.2019 № 231, п. 20.",
    "evidence_frames": [{"timestamp_sec": 8.6, "image_base64": "/9j/…"}]
  }]
}
```

- `POST /api/v1/analyze` — multipart `file`, ответ `{"job_id": "..."}`. Кейс требует `.mov` около 29 МБ;
  `.mp4` и предел 200 МиБ — расширения команды.
- `GET /api/v1/jobs/{id}` — строго схема ТЗ: `status` ∈ `processing | done | failed`, при `done` — `verdict` и `violations`.
- `GET /api/v1/jobs/{id}/details` — для нашего UI. Эталон формата: `docs/frontend/mock_details*.json`.
  Верхний уровень: `status`, `verdict`, `progress {stage, value}`, `stages[]`, `duration_sec`, `processing_sec`,
  `rules_checked`, `preview_url`, `timeline {key: [[t0, t1], …]}`, `timeline_labels {key: подпись}`.
  По нарушению: поля жюри + `type_id`, `timecode_end_sec`, `confidence`, `confidence_level` (low/medium/high),
  `observed` («что видно»), `why` («почему может быть нарушением»), `rule {document, point, quote, url} | null`.
- `X-API-Key` обязателен на всех `/api/*`, без него `401`. Ключ из переменной окружения.
- Задачи переживают рестарт (SQLite), незавершённые ставятся в очередь заново.
- Бэк делает h264-превью для плеера в браузере (`.mov` может быть HEVC).
- Перед F2/B1 согласовать отображение источника без точного пункта (FAQ31) и неполного ответа;
  wire contract и моки не менять без синхронизации. `rule:null` не закрывает нормативную привязку.
- Перед F3/B3 согласовать защищённую раздачу preview: `<video src>` не передаёт `X-API-Key`,
  основной API-ключ нельзя передавать в URL. Отсутствующее превью не блокирует карточки/JPEG.
- F6 проверяет согласованность `/jobs/{id}` и `/details` на реальном backend, публичный URL и офлайн-обработку.

## 6. Интерфейс

Один экран, три состояния:

1. **Загрузка** — перетаскивание файла, проверка формата и размера.
2. **Обработка** — этапы с прогрессом: декодирование → люди и предметы → анализ сцены → проверка находок.
3. **Результат**:
   - баннер вердикта «Нарушение не обнаружено» или «Обнаружены признаки возможных нарушений»;
   - плеер F3 с метками — полезное улучшение после обязательных карточек;
   - дорожки таймлайна состояний F4 — дополнительная объяснимость после основной приёмки,
     только если backend возвращает реальные интервалы;
   - карточка на каждое нарушение: тип, таймкод, кадры с рамкой, «что видно», «почему это может быть нарушением»,
     норматив с цитатой и ссылкой, уверенность;
   - плашка «Результат — подсказка для проверки человеком».

Приоритет реализации UI: F1 → F2 → F5 → F6; F3 после F2/B3 при наличии времени, F4 после F6.
Новый тип события не должен ломать UI. Ошибка, пустые доказательства и противоречивый verdict
